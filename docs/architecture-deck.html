Bedrock 기반 자동 장애 분석 엔진

알림이 뜨면,
원인 분석까지 자동으로.

쿠버네티스에서 알림이 발생하면 — 온콜이 Grafana 를 뒤지기 전에 — 분석 엔진이 로그·메트릭·배포 이력을 모아 1차 원인 분석 리포트를 Slack 과 상황판에 자동으로 붙여준다.

LLM = 분석만 (조치 0, read-only) Amazon Bedrock · Claude Sonnet 4.6 허브 EKS self-host finviz 스타일 상황판
01 — 개요
왜 만들었나

알림은 오는데, 원인은 사람이 찾는다

메트릭·로그·배포 이력은 다 흩어져 있고, 새벽에 알림을 받은 사람이 매번 손으로 추적한다. 그 1차 추적을 엔진이 대신한다.

지금까지

  • Slack 에 알림만 "뭔가 터졌다"
  • 온콜이 Grafana·Loki·ArgoCD 를 직접 뒤짐
  • 알림 폭풍이 오면 어디가 진짜 원인인지 안 보임
  • 매번 같은 조사를 처음부터

엔진 도입 후

  • 알림에 원인 가설 + 증거 링크가 자동으로 붙음
  • 수십 개 알림을 인시던트 1건으로 묶어 분석
  • 상황판에서 전 클러스터 상태를 한눈에
  • 조사 과정을 그대로 보여줘 10초 내 재검증
02 — 문제
전체 흐름 · 한 장 요약

알림 → 리포트까지 다섯 단계

입력Alertmanager알림 발생 → webhook 즉시 수신(202)
→
① 걸러내기게이트중복 억제 · 인시던트로 묶기 · 예산 체크
→
② 모으기Context Pack로그·메트릭·배포 이력을 요약해 압축
→
③ 분석Bedrock원인 가설·증거·신뢰도 생성
→
출력Slack + 상황판리포트 발송 · 히트맵에 표시
핵심은 게이트다. 알림 폭풍이 와도 싼 필터로 먼저 걸러서, Bedrock 은 '진짜 인시던트'만 분석한다 — 비용은 통제되고, LLM 은 압축된 사실 위에서 합성(판단)만 한다.
03 — 흐름도
설계 원칙 · 쉽게

네 가지만 기억하면 된다

🧠

LLM 은 '분석가', '작업자'가 아니다

원인을 추론할 뿐 조치는 절대 실행하지 않는다. 모든 데이터는 read-only. 틀린 자동조치의 위험을 원천 차단.

🧩

알림이 아니라 '인시던트' 단위

노드 1대가 죽으면 알림 35개 — 하지만 원인은 1개. 묶어서 한 번만 분석한다.

📊

덤프하지 않고 '계산된 사실'만

로그 수만 줄을 통째로 넣지 않는다. 신규/급증 패턴, 평소 대비 몇 배 — 요약해서 넣는다.

🔎

결론보다 '조사 과정'을 보여준다

가설마다 증거·신뢰도, 그리고 "무엇을 못 봤는지(data gaps)"까지. 틀린 고확신보다 정직한 불확실성.

04 — 원칙
① 게이트 · 비용과 노이즈를 먼저 잡는다

Bedrock 앞의 싼 필터 3단

폭주는 평상시가 아니라 장애 중(알림 폭풍 = 호출 폭증)에 터진다. 그래서 LLM 전에 결정론적 코드로 거른다.

G1 · 중복 억제

같은 알림은 한 번만

동일 알림이 12시간마다 재통지돼도 재분석하지 않는다. 해소되면 쿨다운 해제.

G2 · 인시던트 조립

관련 알림을 묶는다

같은 클러스터·네임스페이스의 알림을 5분 창으로 하나의 인시던트로. 폭풍이면 "대규모 장애 모드".

G4 · 예산

돈이 새지 않게

인시던트당 토큰 상한·일일 상한. 기본은 critical 만 자동, warning 은 필요할 때 수동.

걸러진 모든 알림은 메트릭으로 기록된다 — 억제 계층 자체도 관측 대상.
05 — 게이트
② Context Pack · LLM 에 줄 '압축된 사실'

흩어진 신호를 한 곳에 모은다

게이트를 통과한 인시던트에 대해, 결정론적 코드가 아래를 모아 요약한다. 소스가 죽어도 멈추지 않고 "못 본 부분"으로 표시한다.

📜

로그

Loki — 에러·연결 실패 패턴을 넓게 검색, 색코드 제거 후 핵심만

📈

메트릭

Thanos — 전 클러스터 파드·워크로드·CPU/메모리·발화 알림

🚀

배포 이력

ArgoCD sync·k8s 이벤트 — 원인 1순위 신호(최근 배포)

🧾

메타

인시던트 현재 상태·묶인 알림·심각도

멀티클러스터 트릭: 엔진은 허브에 있어 스포크 API 를 직접 못 본다 → 전 클러스터로 이미 모이는 Thanos(메트릭)·Loki(로그)만 사용해 모든 클러스터를 커버.
06 — 수집
③ 분석 · 실제 사례

Bedrock 이 로그를 읽고 원인을 짚는다

# Context Pack (요약) incident: tle-api CrashLoopBackOff pod: tle-api-...-vwslp restarts: 3 ready: now true # logs (Loki, 12h) Prisma P1001: Can't reach database server (RDS:3306) cpu: 0.0 mem: 72Mi
결론 confidence · high

tle-api 가 시작 직후 RDS MySQL 연결 실패(Prisma P1001)로 반복 크래시 → CrashLoopBackOff. 현재는 회복(Ready)됐으나 RDS 접근 문제 해소는 미확인 — 재발 가능.

증거
  • Loki 로그에 P1001 "Can't reach database" 반복
  • 재시작 3회 — 외부 일시요인보다 내부 반복 오류 패턴
  • CPU 유휴 → OOM 가능성 낮음
못 본 것 (data gaps)
  • RDS 측 커넥션 한도 / 보안그룹 — 토폴로지 미수집
신뢰는 결론이 아니라 조사 과정에서 나온다 — 증거·신뢰도·못 본 것을 전부 드러낸다. 리포트 렌더링은 코드가, LLM 은 데이터만.
