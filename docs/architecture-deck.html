Bedrock 기반 자동 장애 분석 엔진

알림이 뜨면,
원인 분석까지 자동으로.

쿠버네티스에서 알림이 발생하면 — 온콜이 Grafana 를 뒤지기 전에 — 분석 엔진이 로그·메트릭·배포 이력을 모아 1차 원인 분석 리포트를 Slack 과 상황판에 자동으로 붙여준다.

LLM = 분석만 (조치 0, read-only) Amazon Bedrock · Claude Sonnet 4.6 허브 EKS self-host finviz 스타일 상황판
01 — 개요
왜 만들었나

알림은 오는데, 원인은 사람이 찾는다

메트릭·로그·배포 이력은 다 흩어져 있고, 새벽에 알림을 받은 사람이 매번 손으로 추적한다. 그 1차 추적을 엔진이 대신한다.

지금까지

  • Slack 에 알림만 "뭔가 터졌다"
  • 온콜이 Grafana·Loki·ArgoCD 를 직접 뒤짐
  • 알림 폭풍이 오면 어디가 진짜 원인인지 안 보임
  • 매번 같은 조사를 처음부터

엔진 도입 후

  • 알림에 원인 가설 + 증거 링크가 자동으로 붙음
  • 수십 개 알림을 인시던트 1건으로 묶어 분석
  • 상황판에서 전 클러스터 상태를 한눈에
  • 조사 과정을 그대로 보여줘 10초 내 재검증
02 — 문제
전체 흐름 · 한 장 요약

알림 → 리포트까지 다섯 단계

입력Alertmanager알림 발생 → webhook 즉시 수신(202)
→
① 걸러내기게이트중복 억제 · 인시던트로 묶기 · 예산 체크
→
② 모으기Context Pack로그·메트릭·배포 이력을 요약해 압축
→
③ 분석Bedrock원인 가설·증거·신뢰도 생성
→
출력Slack + 상황판리포트 발송 · 히트맵에 표시
핵심은 게이트다. 알림 폭풍이 와도 싼 필터로 먼저 걸러서, Bedrock 은 '진짜 인시던트'만 분석한다 — 비용은 통제되고, LLM 은 압축된 사실 위에서 합성(판단)만 한다.
03 — 흐름도
상세 시퀀스 · 알림 1건이 들어오면

순서대로 이렇게 동작한다

현재 동작추가로 붙일 수 있는 것(로드맵)
1
Alertmanager
알림 발화 Prometheus/Thanos Ruler 룰 위반 → Alertmanager. critical/warning 이 continue 복사로 analyzer 에 전달(기존 라우팅 유지).
2
Analyzer
webhook 수신 → 즉시 202 POST /webhook 받자마자 응답, 처리는 백그라운드(폭풍에도 블로킹 0).
3
Gate · G1
중복 억제 fingerprint 쿨다운 — 같은 알림 재통지돼도 재분석 0.
4
Gate · G2
인시던트로 묶기 같은 cluster·ns 알림을 5분 창으로 1건 조립. 15개↑면 "대규모 장애 모드".
5
Gate · G4
예산 체크 critical 자동 / warning 보류. 토큰·일일 상한 통과해야 다음으로.
6
Context Pack
사실 수집·압축 (LLM 없음) Loki 로그 + Thanos 메트릭(워크로드·CPU/Mem·문제파드) + ArgoCD/k8s 이벤트.➕ 추가 가능 — 평소 대비 baseline diff · Drain3 로그 템플릿 · 토폴로지 홉 판정
7
S3 Vectors
유사도 체크 (메모리) 시그니처 임베딩(Titan) → 과거와 코사인 유사도 ≥0.90(재발)이면 Bedrock 스킵하고 과거 결론 즉답(비용↓). 아니면 다음으로.
8
Bedrock
원인 분석 (Sonnet 4.6) 시스템프롬프트(read-only·인젝션 방어)+Context Pack → 구조화 JSON(가설·증거·confidence·data_gaps). 실패 시 degraded.➕ 추가 가능 — confidence 낮으면 MCP 도구로 2단 심층 조사 에이전트
9
출력
발송 · 표시 · 기억 코드가 렌더 → Slack + 상황판/히트맵 + 성공 분석은 S3 Vectors 에 적재.➕ 추가 가능 — 👍/👎 피드백 루프(틀린 분석을 메모리에 반영)
10
해소
자동 정리 AM resolved → 인시던트 자동 해소 → 상황판에서 사라짐(안전망 포함).
04 — 상세 동작
수집 & 판단 · 어떤 데이터를, 무엇을 기준으로

데이터는 이렇게 가져오고, 이렇게 판단한다

📥 데이터 — 어디서·어떻게

로그Loki LogQL {cluster,ns} |~ "err|fail|refused|timeout|rds|sql…" · ANSI 제거 · 최근 12h · 상위 N줄
워크로드kube_pod_info·kube_pod_status_ready + relabel 룰 join → 워크로드별 ready/desired (Deployment·STS·DS·Rollout)
리소스container_cpu/memory × relabel join → 워크로드별 CPU·Mem (파드→워크로드 매핑)
이상신호ALERTS{firing} · restarts increase(15m) · last_terminated_reason(OOMKilled 등)
배포ArgoCD sync 이력 · k8s Events — 최근 변경(RCA 1순위 신호)

⚖️ 판단 — 무엇을·어떤 기준

중복 G1fingerprint 쿨다운 1h — 같은 알림 재분석 0
묶음 G2cluster+ns · 5분 상관창 → 인시던트 1건 / 15개↑ = 대규모 장애 모드
예산 G4critical=자동 · warning=보류 · 인시던트당 토큰·일일 상한
문제 파드현재 not-ready 또는 최근 15분 재시작 ≥1 (누적 아님 → 회복되면 빠짐)
타일색 = CPU/Mem 부하 or ready/desired · 크기 = replica 수
신뢰도데이터 충분=high · 부족=low + 못 본 것(data_gaps) 명시
멀티클러스터 트릭: 엔진은 허브에 있어 스포크 k8s API 를 직접 못 본다 → 전 클러스터로 이미 모이는 Thanos(메트릭)·Loki(로그)만 써서 모든 클러스터를 커버.
05 — 수집 & 판단
메모리 & 유사도 · 구현 완료 · 동작 중

"이거 지난번 그거 아냐?"를 즉답

반복 재발 장애에 매번 풀 분석하면 느리고 비싸다. 과거 인시던트를 벡터로 기억해 두고, 새 인시던트가 오면 유사도로 먼저 맞춘다. 실제 동작 검증 — 재발 알림을 유사도 0.96으로 잡아 Bedrock 없이 즉답.

1 · 시그니처인시던트 지문alertname 집합 + 서비스 + 핵심 로그 템플릿을 하나의 시그니처로
→
2 · 임베딩Bedrock Titan시그니처를 벡터로 변환
→
3 · 벡터 검색S3 Vectors과거 인시던트와 코사인 유사도 비교
→
4 · 판정유사 ≥ 0.95"3일 전 INC-042 와 동일, 재발 3회" 즉답 → 풀 분석 스킵
왜 S3 Vectors? OpenSearch Serverless 대비 ~30배 저렴(월 $10대) · idle 비용 0 — 1인 운영 규모에 맞음.
유사해도 항상 "풀 재분석" 버튼 제공 — 캐시가 틀릴 수 있으니 사람이 언제든 덮어쓴다.
06 — 메모리·유사도
설계 원칙 · 쉽게

네 가지만 기억하면 된다

🧠

LLM 은 '분석가', '작업자'가 아니다

원인을 추론할 뿐 조치는 절대 실행하지 않는다. 모든 데이터는 read-only. 틀린 자동조치의 위험을 원천 차단.

🧩

알림이 아니라 '인시던트' 단위

노드 1대가 죽으면 알림 35개 — 하지만 원인은 1개. 묶어서 한 번만 분석한다.

📊

덤프하지 않고 '계산된 사실'만

로그 수만 줄을 통째로 넣지 않는다. 신규/급증 패턴, 평소 대비 몇 배 — 요약해서 넣는다.

🔎

결론보다 '조사 과정'을 보여준다

가설마다 증거·신뢰도, 그리고 "무엇을 못 봤는지(data gaps)"까지. 틀린 고확신보다 정직한 불확실성.

07 — 원칙
③ 분석 · 실제 사례

Bedrock 이 로그를 읽고 원인을 짚는다

# Context Pack (요약) incident: tle-api CrashLoopBackOff pod: tle-api-...-vwslp restarts: 3 ready: now true # logs (Loki, 12h) Prisma P1001: Can't reach database server (RDS:3306) cpu: 0.0 mem: 72Mi
결론 confidence · high

tle-api 가 시작 직후 RDS MySQL 연결 실패(Prisma P1001)로 반복 크래시 → CrashLoopBackOff. 현재는 회복(Ready)됐으나 RDS 접근 문제 해소는 미확인 — 재발 가능.

증거
  • Loki 로그에 P1001 "Can't reach database" 반복
  • 재시작 3회 — 외부 일시요인보다 내부 반복 오류 패턴
  • CPU 유휴 → OOM 가능성 낮음
못 본 것 (data gaps)
  • RDS 측 커넥션 한도 / 보안그룹 — 토폴로지 미수집
신뢰는 결론이 아니라 조사 과정에서 나온다 — 증거·신뢰도·못 본 것을 전부 드러낸다. 리포트 렌더링은 코드가, LLM 은 데이터만.

10 — 배포
로드맵 · 앞으로 할 것

다음 단계 — 무엇을, 왜

현재 "알림→분석→리포트→상황판→유사도 캐시"까지 동작. 더 똑똑하고 정확하게 만들 다음 과제들.

정확도

Context Pack 완결

이게 뭔지 — LLM 에 주는 사실을 더 풍부하게.
할 일 — 어제/지난주 대비 메트릭 baseline, Drain3 로그 템플릿 압축, pod→node→svc→RDS 토폴로지 홉 판정.

안정성

상태 영속화

이게 뭔지 — G1/G2 인시던트 상태가 지금은 메모리라 파드 재시작 시 리셋.
할 일 — PVC 또는 Redis 로 이전.

자가개선

피드백 루프

이게 뭔지 — 분석이 맞았는지 사람이 평가.
할 일 — Slack 👍/👎 버튼 → "이 패턴 과거 분석 틀림"을 메모리에 반영.

도메인 지식

족보/런북 RAG

이게 뭔지 — 과거 트러블슈팅 문서를 분석에 주입.
할 일 — 문서 임베딩 → S3 Vectors → Context Pack 에 관련 런북 삽입.

심층 조사

에이전트 루프

이게 뭔지 — 애매한 케이스(confidence low)를 자동으로 더 파고들기.
할 일 — MCP 도구(read-only)로 2단 bounded 조사, 8-call 상한.

품질 측정

평가 · 트레이싱

이게 뭔지 — 분석 품질을 수치로 관리.
할 일 — LLM-as-judge 평가 + OTel GenAI 트레이싱(토큰·지연·비용).
